# 02 · 谱面结构与音符分类

## 1. 谱面文件

每首歌一个 `chartdoc/1` JSON，顶层是扁平的 `notes` 数组，节点有两种形态：

* **单节点**：`{timeMs, type, position, size, direction}`
* **容器**：`{type: "long" | "guide", node: [ ...子节点 ]}`，子节点里
  `position` 可以是数字、可以是 `"auto"`，也可以是 `null`（沿用上一个）。

`position` 是**左边界格位**，`size` 是宽度（格），所以中心格位是
`position + size/2`。谱面共 **24 格**（`0..24` 是中心的范围，左边界因此能到负数）。

## 2. 只有 5 种类型，但游戏只讲了 4 种音符

游戏自带教程（`MasterText.json` 的 `Help_SubCategory_Description_90003`）说的是：

> **Trace Notes**: Unlike regular Slide Notes, Trace Notes do not require you to
> tap in time with the Hit Line at the start or end points. **You simply need to
> keep the screen tapped as the Notes pass through the Hit Line.**

也就是 Tap / Slide / Flick / **Trace** 四种。但谱面文件里出现了 5 种 `type`：

| 谱面 type | 对应 | 说明 |
| --- | --- | --- |
| `tap` | Tap | 单节点 |
| `flick` | Flick | 单节点，`direction` = up / left / right |
| `long` | Slide | 容器，按住 + 沿轨迹走 |
| `guide` | **不一定** | 容器。**可能是 Trace，也可能只是视觉参考线** |
| `trace` | Trace 的采样点 | 单节点，没有自己的 `timeMs` 之外的时序语义 |

关键就在 `guide`：它是个容器，长得和 `long` 一样，但绝大多数不是音符。

## 3. `guide` 三分类（全库 614 条）

判据不能只看"有没有可见节点"，也不能看"是不是容器"。最后落在**子节点的语义**上：

| 子节点特征 | 条数 | 是什么 | 怎么处理 |
| --- | --- | --- | --- |
| 跨度内**含 `trace` 节点** | 41 | **Trace 音符** | 位置用 trace 节点的格位 |
| 子节点里有 **`positionAuto: true`** | 253 | **自动布点的滑条**（就是画出来的那串 Notes） | 位置用头尾插值 |
| 两者都有 | 8 | Trace 音符 | 归第一类 |
| 两者都没有 | 328 | 视觉参考线（设置里的 "Guideline"） | **跳过** |

> 注意 41 + 253 - 8 = 286，加 328 = 614。三个数都对得上。

### 3.1 为什么 `guide` 不能整类当音符

1.4.9c 试过把 614 条全当长条发，结果**开局就往屏幕上按 3 根手指、按住 10 秒**，
整局全 miss。原因是开头那几条 `1263~11368`、`11368~22104` 的 guide 是
**铺满 10 秒的背景参考线**，`pos` 恒为 0、`size` 恒为 24 —— 手指按在屏幕正中间
十秒，后面所有音符都被这根"假手指"占着槽位。

反过来的错误是 1.4.9a/b：只发 `visible: true` 的节点。
但 guide 的**头尾往往 `visible: false`**，可见的那串反而是中间段，
于是只按到了半截。

### 3.2 `positionAuto` 长什么样

```
100040 结尾：
{
  "type": "guide",
  "node": [
    {"pos": 0,  "size": 24, "t": 106105, "visible": false},   ← 头（全宽）
    {"pos": "auto", "t": 106131}, ... × 36                      ← 可见，画出来的 Notes
    {"pos": 9,  "size": 6,  "t": 107053, "visible": false}     ← 尾
  ]
}
```

`pos: "auto"` 的节点**没有坐标**，它是"引擎自己按头尾在这段时间里均匀撒点"。
所以位置只能由 `_path_of(inner)` 按头尾插值出来 —— 这也正好保证**不会出屏**
（见下一条）。

## 4. 用 guide 自己的路径会甩出屏幕

guide 的 `pos` 是**容器自己的轨迹**，和内部音符的格位不是一回事。
`100040` 的 `54947~58104` 那对 guide：

```
guide A: pos 18 → 24    （中心 21 → 27）
guide B: pos 0  → −6    （中心 3  → −3）
```

中心跑到 **−3 和 27**，超出 `0~24` 格。照抄这条路径，手指会跑到屏幕外
（实测 −2.6 / 26.6 格），游戏当然不认。
而这一段的 `trace` 节点只在**格位 3 和 21** —— 所以正确做法是
**跨度用 guide 头尾、位置用 trace 节点的格位**。

## 5. `trace` 节点怎么串成一根手指

`trace` 是采样点，一个 Trace 音符通常有几十个点。分串规则：

```python
TRACE_RUN_MAX_GAP_S = 0.100   # 相邻点时间间隔 ≤ 100ms
TRACE_COVER_LANE    = 1.5     # 且格位连续（≤ 1.5 格）
```

两个条件**同时**满足才算同一条；否则断开。为什么不能只看时间：
`100060 / 100047 / 100082` 有**同刻不同格位**的 trace（双押），
只按时间会把两根并成一根，手指就要瞬移。

串好之后：

* 跨度为 `[第一个点, 最后一个点]`；
* 只有一个点时，至少按住 `TRACE_MIN_HOLD_S = 0.120s`（否则游戏来不及判定）；
* 相邻两条长条结束/开始相差 ≤ `TRACE_JOIN_MS = 30ms` 且同一轨道 → 直接接上，
  不换手指（换手指会漏一个 `TRACKING_ID` 周期）。

## 6. "已经覆盖了"要按轨迹判断，不能只看头

一条长条可能从格 21 一路滑到格 3。如果判断"这条 trace 是否已被覆盖"时
只看**长条头部的格位**，就会认为格 3 那一刻没有手指，于是多发一根 —— 多余的手指
会和滑条抢触发。正确做法是**按长条轨迹插值**取那一刻手指的格位，
容差用**这条 trace 自己的 `size/2`**（`100109` 的 trace 宽 12 格，用固定 1.5 格
会把明明已经被盖住的点再按一次）。

## 7. 头部撞车：接管而不是丢弃

guide / trace 的头部经常和一条真实音符**同刻同格**（差 ≤ 15ms、≤ 1.5 格）。
这时那个 tap 就是这条长条的"头"：

* 头是 `tap` → 删掉 tap，用长条代替（一根手指又点又按）；
* 头是 `flick` → **也要接管**，把长条的头改成"先朝该方向滑一下、再按住走完"；
* 头是别的（比如同位置还有个 flick 加 hold）→ 放弃这条长条（两种手法没法同时做）。

> 1.5.0 在这里犯过错：遇到 flick 头直接 `bad = True` 丢掉，正好丢了
> `100040` 结尾那条全宽上滑 —— 于是"上滑之后全 miss"。
