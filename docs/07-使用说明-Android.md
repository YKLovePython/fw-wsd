- 包名：`com.fwwsd.app`
- 版本：`1.5.1`（versionCode 18）

## 〇、1.5.1 又修了什么：结尾那一下

### 1. 现象

100040 最后：一个**全宽上滑**之后，后面的全 miss。

### 2. 原始数据

```
106105  flick dir=up  pos=0 size=24（全宽上滑）
106105  guide  106105 ~ 107053（0.95 秒）
         头 pos=0 size=24（不可见）
         36 个 pos="auto" 的节点（可见）
         尾 pos=9 size=6（不可见）
```

也就是说：**最后一个音是「全宽上滑 + 再按住 0.95 秒」**。我们只做了那个上滑，
后面那段 hold 完全没按。

### 3. 根因：「含 `positionAuto` 的 guide」整类被跳过

谱面里 guide 有五种，我们之前的判据只看「里面有没有 `trace` 节点」：

| guide 类型 | 全库 | 1.5.0 | 1.5.1 |
| --- | --- | --- | --- |
| 含 `trace` 节点 | 41 | ✅ 发 | ✅ 发 |
| **含 `positionAuto` 节点** | **253** | ❌ 跳过 | ✅ **发** |
| 两者都有 | 8 | ✅ 发 | ✅ 发 |
| 都没有（视觉参考线） | 328 | 跳过 | 跳过 |

那 253 条 auto guide 全部在屏幕范围内（头尾格位都在 0~24），时长 165 条 ≤0.3s、
86 条 0.3~1s、2 条 >1s；头是 tap 的 219 条、flick 的 8 条、没有头的 18 条。

游戏教程原话：Trace 音符「保持屏幕被按住，让 **Notes** 从判定线上过去」——
`positionAuto: true` 的节点正是**画出来的那一串 Notes**（`visible: true`），
头尾反而是不可见的起终点。例：`100008` 有一条 `18474~18631`（0.16s），
头格 15、尾格 21，auto 节点在中间 —— 就是一小段滑条。

### 4. 修法

- 含 `positionAuto` 的 guide：跨度用 guide 的头尾，**位置用 `_path_of(inner)`
  插值出来的轨迹**（auto 节点没有坐标，按头尾插值，不会出屏）；
- **头是 flick 的也能接管**：把长条的头改成「先朝给定方向滑一下、再按住走完」，
  一根手指做完（以前遇到 flick 头会直接丢掉）；
- 头是 tap 的照旧接管；
- 仍然跳过「既没 trace 也没 auto」的 328 条（那批就是 1.4.9c 崩掉的视觉线）。

### 5. 复查

| 检查 | 结果 |
| --- | --- |
| 225 个顶层 trace 节点有没有手指 | **225 / 225** |
| 长条内部 100 个 trace 子节点 | **100 / 100** |
| 全库 trace / auto 长条 | 321 条，遍及 34 张谱 |
| 排程状态违规 | **0** |
| 同时按着的手指峰值 | 6 指 |

### 6. 1.5.0 的问题（已修）

1.5.0 只发了含 `trace` 的 guide，漏了 auto 那 253 条；另外还有两个小 bug：
含 trace 的 guide 照抄 guide 自己的路径（`100040` 那对会甩出屏幕，手指跑到
-2.6 / 26.6），以及「已覆盖」判断只看长条头格位（把旁边真正的 trace 音符误杀）。
这两个 1.5.0 已修，1.5.1 在其基础上加了 auto。

## 附：1.5.0 之前的历史（1.4.9c 为什么错）

### 1. 背景：1.4.9c 是错的，d 是对的

c 把**所有** guide 容器（614 条）都当长条发 → 开局往屏幕上按 3 根手指、按 10 秒，
整局全 miss。**所以「guide = 音符」是错的。**

游戏自己的新手说明（`MasterText.json`）只有 **4 种音符**：Tap / Slide / Flick /
**Trace**，原文：

> **Trace Notes** … do not require you to tap in time with the Hit Line at the
> start or end points. **You simply need to keep the screen tapped as the Notes
> pass through the Hit Line.**

谱面里 5 种类型对照：`tap`→Tap、`flick`→Flick、`long`→Slide、
**`trace`（含 trace 的 `guide`）→Trace**，其余 573 条 guide 是视觉参考线。

### 2. d 之后还剩 20 个 trace 点没人按 —— 1.5.0 修的就是这个

我按「**每个 trace 节点那一刻，它自己的宽度（size/2）里有没有手指**」全库扫了一遍。
d 的时候 225 个里有 **20 个没有手指**，原因是两个 bug：

**A. 含 trace 的 guide，它的路径会甩出屏幕（9 个）**

`100040` 在 54947~58104 有一对 guide，原始数据是 `pos 18→24`（中心 21→**27**）
和 `pos 0→-6`（中心 3→**-3**）——**都超出 0~24 格**。而这段里的 trace 节点全在
**格位 3 和 21**（guide 的头）。也就是说：真正的键在 3 和 21，guide 的路径只是
一条甩出去的线。d 照抄路径，手指跑到 **-2.6 / 26.6**（屏幕外），
到衔接处 55578 / 56210 / 56842 / 57473 就离开了真正的键 → 漏。

**B. 同一时刻不同格位的 trace 被并成一根（9 个）**

分串规则只看时间间隔。例：`100060` 73272 同时有**格位 8 和 16** 两个 trace
（双押），只按了第一根。`100047` 2 处、`100082` 1 处同理。

**C. 2 个**：`100040` 24000、`100063` 60824。

### 3. 1.5.0 的修法

- **含 trace 的 guide**：跨度还是用 guide 的头尾，**位置改用内部那些 trace 节点的
  格位**（不再用 guide 自己的路径）。100111 那种（轨迹和 trace 同格）不变，
  100040 那种（轨迹甩出屏）就修好了；
- **trace 分串先按格位、再按时间**：同一时刻不同格位 → 各自一根手指；
- **「已覆盖」的判断按轨迹插值**，并且容差用**这条 trace 自己的半宽**——以前只看
  长条的头格位，会把「从 21 滑到 3 的长条」当成一直停在 21，把真正的 trace 音符
  误杀（`100040` 24000 就是这么丢的）。

### 4. 复查结果

| 检查 | 结果 |
| --- | --- |
| 225 个顶层 trace 节点有没有手指 | **225 / 225** |
| 长条内部的 100 个 trace 子节点 | **100 / 100** |
| 全库 trace 长条 | 101 条，遍及 13 张谱 |
| 排程状态违规 | **0** |
| 同时按着的手指峰值 | 6 指 |

### 5. 怎么测

打 `100040`（trace 最密、也是这次修得最多的）或 `100111`，对比 miss 数。
日志会打：

```
谱面：100040 / EXPERT，1888 个动作，offset 0ms
  对账：音符 715（tap 508 · flick 68 · 长条 139）｜guide 0 / 116 条· trace 7 / 41 条· critical 10
```

### 4. 怎么测

先装 **e** 打一遍确认基线正常（和 1.4.7 一样），再装 **d** 打同一首对比 miss 数。
建议用 trace 最密的 `100111`（47 个 trace）或 `100040`（41 个）。

日志会多一行 trace 的账：

```
谱面：100040 / EXPERT，1950 个动作，offset 0ms
  对账：音符 714（tap 508 · flick 68 · 长条 138）｜guide 0 / 116 条· trace 6 / 41 条· critical 10
```

- `trace X / Y`：Y 是这张谱的 trace 节点总数，X 是 d 真的发出去的条数；
- `guide 0 / 116`：guide 节点总数（d 里仍然全跳过，只把含 trace 的那部分当 trace 发）。

## 一、1.4.7 改了什么（历史，一直保留到现在）

### 1. 「同一个位置一串连续上滑」不再 miss

谱面里有两种密集上滑：

- **一堵墙**：同一位置每 26~27ms 一个上滑、连续 15 个（`100040 EXPERT` 有两处）；
- **一串**：同一位置每 105~180ms 一个上滑，连续十几个。

以前脚本是「每个音符都做一次完整的按下 → 上划 → 抬起」。一个手势要跨 70ms，
而墙上两个音符只隔 26ms，只能排成 4 根手指在同一个点上轮流起落；手机稍微一抖
（±15ms），边缘就全压在噪声上，整段掉。

1.4.7 在**生成动作表那一侧**加了一条规则：同一位置、连续 ≥3 个上滑、相邻间隔
<60ms 时，合并成**一根手指的连续摆动**——按住不放，每个音符向上划一次、两拍之间
回落，最后才抬手。人手在那种地方本来也是这么做的。

- 只命中 `100040 EXPERT` 两处和 `100015 EXPERT` 一处；
- 孤立的单个上滑、普通点击、长条**一个字节都没改**；
- PC 版和手机版共用同一张表，所以电脑上打出来会和以前一样。

### 2. 打歌期间不再和注入线程抢 CPU

以前拿到锚点后**忘了关视觉闸门**：整首歌每一帧（60fps）都在解码回调线程上跑一遍
整屏亮度采样。1.4.7 起：

- 锚点一拿到就关掉视觉采样（电脑版一直是这样做的）；
- 注入期间把引擎线程提到高优先级，打完降回去；
- 悬浮条只在状态变化时重画，不再每 300ms 新建两个背景；
- 日志的「迟到」改成 `最迟 +Xms（p95 +Yms）`，一眼看出是常态抖动还是被打断。

### 3. 砍掉没用的功能

| 砍掉的 | 原因 |
| --- | --- |
| 「原地再演」循环 + 它那 60 行坐标盲点链 | 电脑版验证过的是「回选曲页」，盲点链出错就卡死 |
| 「打歌时隐藏悬浮窗」 | 死开关，没有任何代码读它 |
| 视频流宽度 / 30·60fps 选择 | 1280/60 是判定线的标定值，调低会认不出演奏画面 |
| OCR 开关 | 关掉之后根本不会点难度，等于残废 |
| 「自适应判定线」开关 | 逻辑保留（写死开），它是换机型/游戏改版时唯一的自救 |
| 「右下角 / 确定 / 评级页」坐标输入框 | 默认值已真机标定，手滑改错一个整条循环就静默失效 |
| 「自动循环」开关 | 和局数 chips 打架，现在只留局数（∞ / 1 / 3 / 5 / 10） |
| 1.4.6_b 的「先回桌面再拉起」 | 已证伪（偏移真因是游戏内的音符延迟设置），每局白等 5 秒 |

**保留**：配对（自动读码 + 手动兜底）、OCR 选曲/选难度、offset、日志、连接/断开、
取消任务、自动息屏还原。

### 4. 锚点策略统一

固定用「**加载页优先、判定线兜底**」——和电脑版同一条。加载页是整屏由亮变黑，
信号大、掉几帧也不怕；判定线只有 1~2px 的淡入，最怕掉帧。

## 二、它是怎么工作的

1. App 里打包了一份 AOSP 的 `adb`，在手机内部跑一个 adb server，
   通过**无线调试**连回这台手机自己（LADB 走的那条路）。
2. 拿到 shell 后，把 `scrcpy-server` 推上去跑起来，取两样东西：
   - **视频流**：用来「看」画面，判断演奏画面什么时候出现；
   - **控制通道**：注册一块 **UHID 虚拟触摸屏**，游戏会把它当成真实外接触摸屏。
3. 打歌时手指动作全部走 UHID；`input tap` 只用来点菜单。
4. **认字用 OCR**：内置和电脑版同一套 PP-OCR（det + rec），不联网。
   选曲页/难度按钮靠认字定位，不是靠死坐标。

**关于「无障碍」**：App 里有一个无障碍服务，但它**只读、不点、不划、不输入**
（配置里没有 `canPerformGestures`）。唯一作用是配对那一次，把系统对话框里的
6 位配对码读出来。除此之外不看任何东西，也不联网。

## 四、第一次：配对（只做一次）

> 配对的意思是：手机里的 adb 记下这 App 的公钥，以后不用再输码。
> 换 Wi-Fi 网络可能要重做一次（见 FAQ）。

### 第 1 步：打开「读码」开关

1. App 里点 **「开启读码」**。
2. 跳到系统的 **无障碍** 页面。找到 **「fw-wsd 配对码读取」** → 点进去 → 打开。
3. 返回 App，按钮会变成 **「去配对」**。

### 第 2 步：去配对

1. 点 **「去配对」**，App 会跳到系统的 **无线调试** 页。
2. 无线调试是关的先打开。
3. 如果显示灰字 **「不可用（未获允许）」**：关掉无线调试再打开，系统会弹
   「要允许通过此网络进行无线调试吗？」→ 勾「始终允许」→ 确定。
4. 点 **「输入配对码配对设备」**，弹出对话框，里面有 6 位数字。

### 第 3 步：什么都不用做

对话框一出现，App 会自己读到那 6 位数字并完成配对（通知栏弹「✓ 配对成功」）。

然后点 **「连接」**，看到绿点 +「已连接本机 adbd」就成功了。
从这一刻起，读码服务开不开都无所谓了。

> 读不到码？App 里有「读不到配对码？点这里手动输入」的兜底。

## 五、日常使用

**前提：无线调试的开关是开着的。**

App 第一次连上时会自动给自己授一个 `WRITE_SECURE_SETTINGS` 权限
（用 shell 身份执行 `pm grant`）。有了它，App 以后可以自己开关无线调试。

### 第 1 步：连接

打开 App，点 **「连接」**，看到绿点即可。（点「保存任务」时它也会自己连。）

### 第 2 步：设任务

1. 「游戏」卡片 → 选 **Our Notes**（B 站版，`com.bilibili.sirius.official`）。
2. 「曲目」卡片 → 选一首歌（内置 96 首、384 张谱面，不联网）。
3. 选难度（EASY / NORMAL / HARD / EXPERT / SPECIAL）。
4. 「打歌」卡片选**局数**：∞ / 1 / 3 / 5 / 10。
5. 时间微调默认 **0 ms**，一般不用动。

然后点 **「保存任务」**。这一步**不会开始打**，只做三件事：存参数、
把悬浮条挂到屏幕上、顺手连一次 adb。

### 第 3 步：进游戏，把歌选好

打开游戏，**手动进到选曲界面，把要打的那首歌选中**（光标停在那首歌上）。

### 第 4 步：点悬浮条的 ▶

游戏里会出现一条粉色小悬浮条（左上角，可拖动），点 **▶** 才开始执行。

头几秒是准备阶段（连 adb、起录屏、等第一帧、加载 OCR 模型），悬浮条显示
「准备中…」，**不是没反应**；准备完它会自己点一次难度，然后开打。

### 接下来全自动

```
（第 1 局）只点难度（OCR 认 EXPERT / エキスパート …），不翻歌单——歌是你选的
→ 点「决定」进确认页
→ 认出演奏画面 → 算出谱面 0 点 → UHID 注入整首
→ 结算页自动点掉
→ 回选曲页 → 找歌 → 点难度 → 下一局
```

- **停止**：点悬浮条 ■ 或 App 里的「停止」。任务还在，可以再点 ▶ 重来。
- **取消任务**：App 里的「取消任务」，悬浮条收起、通知消失、任务清掉。

## 六、时间微调（offset）

- 默认 **0 ms**；含义是**正数 = 所有落点整体推后，负数 = 整体提前**。
- 判成 **FAST**（出手早了）→ 调大；判成 **SLOW / LATE** → 调小。步进 ±10 ms。
- 调完立即生效并记住。
- **注意**：App 的 offset 和游戏 LIVE 设置里的「ノーツタイミング / 譜面位置」
  效果等价、可以互相抵消。打歌时请把游戏那两个设置固定住（建议归零）——
  之前那次「稳定晚 80~90ms」就是游戏内设置改动造成的，不是 App 的问题。
- 先看日志再动 offset：每局都有「锚点体检」和「链路体检」两行。如果
  `判定线可信`、`加载页差 ±0~30ms`，说明起跑线是准的，这时候才考虑调 offset。

## 七、打歪了怎么办

- **选曲 / 难度**：靠 OCR 认字，不用调坐标。认不出来就看日志里
  「画面 … 选曲页/未识别 …『…』」那一行，把实际文字和它认到的对比。
- **结算导航**：用的是右下角比例坐标（0.899 / 0.956），已真机标定过。
  1.4.7 起界面里不再提供修改入口，避免误改后整条循环静默失效。

## 八、常见问题

### 选曲 / OCR

**日志里一直是「未识别」，认不出选曲页**
- 先确认游戏真的停在选曲页（不是结算页/加载中）。
- 有的 ROM 会拦「应用内截图」：日志写「截图返回的不是 PNG」时，去设置里给
  fw-wsd 开「后台弹出界面」「显示在其他应用上层」，省电策略设「无限制」。
- 截图能出、但字认不出：把日志里那行「画面 … 『…』」发我。

**难度按钮认不到，日志写「没找到 EXPERT 难度按钮」**
- 看日志里更低相似度的候选；如果这版没有 EXPERT（只有 SPECIAL），选 SPECIAL。
- 兜底：脚本不会停，会继续用右下角盲点，但那样不一定能开始。

### 配对相关

**「输入配对码配对设备」是灰的 / 显示「不可用（未获允许）」**
- 这是 Android 的按网络授权：关掉无线调试再打开 → 勾「始终允许」→ 确定。
- 还没好就检查 Wi-Fi 是不是真的连上了。

**读不到配对码**
- 用 App 里的手动输入兜底：最近任务把「设置」和本 App 分屏，把 6 位数字填进来。
- 配对码有有效期，失败了重新拿新码。

**换了 Wi-Fi 之后连不上了**
- 无线调试的授权是**按网络**记的，换网需要重新配对一次。

### 打歌相关

**「8 秒内没解出画面」/「5 秒内一帧都没解出来」**
- 给 fw-wsd 开「后台弹出界面」「显示在其他应用上层」，省电策略设「无限制」。
- 看日志这几行定位：
  ```
  视频会话 1280x590          ← 收到会话包，尺寸对
  解码器就绪 1280x590
  首帧解码成功 1280x590      ← 到这里视频就通了
  ```
  只有「视频会话」→ SPS/PPS 或解码器问题；只有「解码器就绪」→ 有数据但解不出图。

**「点进游戏了却还在一直点右下角」/「45 秒没认出演奏画面」**
- 每 2 秒一行心跳：「帧 / 亮度峰值 / 品红线 / 白线 / 分数」。
  - `分数 0.00` 且白线/品红线都接近 0 → 画面不是演奏页，或判定线位置不同
    （自适应判定线会在 6/12/18/24 秒时自己找一次，日志出现「自适应判定线：白 y=…」）；
  - `帧` 一直不涨 → 视频链路问题，看「视频流已断开 / 已经 …ms 没有解出画面」。
- 常见原因：手机上弹了系统更新/低电量/权限弹窗。清掉再试。

**「两边都 0 分，但画面明明在演奏」**
- 先看 `视频会话 WxH` 和 `屏幕 WxH` 的长宽比是否一致（1280×~590 对 2510×1156）。
- 平板/折叠屏/游戏改版：自适应判定线会自动兜底，日志等那一行出现。

**「认出演奏画面，但音符全错位」**
- 先 ±10 ms 调 offset。
- 如果「越到后面越偏」，是手机掉帧：省电策略设「无限制」、关掉后台应用。

**「同一位置的一串连续上滑仍然掉」**
- 顺手确认游戏的 LIVE 延迟设置没被动过。

**「想确认某一首到底有多少键没发出去」**
- 看日志第二行「对账」：`音符` / `guide` / `trace` / `critical` 几个数就是这首歌的
  指纹，换版本、换机型都能直接对比。

**「某一类键还是按不到」**
- 先看日志「对账」那行：`trace X / Y 条`。X 接近 Y 就说明该发的都发了。
- 如果还漏，把「对账」和「注入完成 … 最迟 +Xms（p95 +Yms）」两行发回来，
  按这两行定位是「没发」还是「发了但迟了」。

**「点了开始，但一直卡在某个界面」**
- 45 秒没认出演奏画面会自动放弃（防止在弹窗上无限点）。

### 其它

**这个 App 会不会偷看我的东西？**
- 无障碍服务只在**当前前台是系统设置**时扫窗口文本，且只有一屏里同时出现
  「配对码」字样和单独一个 6 位数字时才动作，其它一概不看。
- 配置里没开「执行手势」，系统层面就点不了东西。
- OCR 全部本地跑，不联网。
- 不放心的话，配对成功后把无障碍关掉，打歌完全不受影响。

**「不想用了」**
- 直接卸载 App。App 只在 `/data/local/tmp/` 留了一个 `fwwsd-scrcpy.jar`，
  卸载后可用 `adb shell rm /data/local/tmp/fwwsd-scrcpy.jar` 清掉（不清也没影响）。
