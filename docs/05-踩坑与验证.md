# 05 · 踩坑与验证

这一篇记的是**被证伪的假设**。它们比结论更值钱，因为每一条都长得很合理。

## 1. 五个版本，五次证伪

| 版本 | 假设 | 结果 |
| --- | --- | --- |
| 1.4.9a | guide 的**可见节点**就是点击音符 | 失败：只按到中间段，头尾是 `visible:false` |
| 1.4.9b | guide 的可见节点串成滑条 | 失败：`visible:false` 的头尾被跳过；flick 头被直接丢弃 |
| 1.4.9c | **所有** guide 容器都当长条（614 条） | 崩溃：开局按 3 指 10 秒，整局全 miss |
| 1.4.9d | 含 `trace` 节点的 guide 当 Trace 长条 | **成功**（用户真机确认） |
| 1.4.9e | 基线（不做 trace） | 对照组 |
| 1.5.0 | d 的修复版：位置改用 trace 格位、覆盖判断按轨迹 | 成功，但漏了 auto |
| 1.5.1 | 加 `positionAuto` 的 253 条 + flick 头接管 | 待测 |

## 2. 为什么 1.4.9c 会崩得那么彻底

`100040` 前两条 guide 是 `1263~11368`、`11368~22104`，跨度 10 秒，
`pos` 恒为 0、`size` 恒为 24 —— **铺满屏幕的背景参考线**。

把它们当长条发，等于开局就把一根手指按在屏幕**正中央**十秒钟。
音游的触摸槽位是有限的，而且长条会"吸附"最近的触摸点：这根假手指会把
真正该按的音符抢走。所以不是"多按了几个"，是**整局全 miss**。

这也解释了为什么"多发一点总比漏发好"这条直觉是错的：
在触摸判定里，**多发的手指是有害的**，不是无害的冗余。

## 3. 1.4.9b 为什么"合并过、但没用"

b 确实会合并一部分 auto guide，但它的实现里：

```python
if e.kind == "tap":  ...接管
else:                bad = True   # ← flick 头直接丢弃
```

而 `100040` 结尾那条的头正好是 `flick`（全宽上滑），所以 b 对它**什么都没做**。
另外 auto 节点没有坐标时 b 的路径算错。

**所以"1.4.9b 没用"不能证明 auto guide 不是音符** —— 它只是没被正确实现。
这是最危险的一类证据：**失败的实验不能否证假设，只有正确的实验才能。**

## 4. 两个"看起来对"的错误判据

### 4.1 用 guide 自己的 `pos` 当轨迹

guide 的 `pos` 是**容器自己的轨迹**，和内部音符无关。`100040` 的
`54947~58104` 那对是 `18→24` / `0→−6`（中心 `21→27` / `3→−3`），
照抄会让手指跑到 **−2.6 / 26.6 格**，也就是屏幕外。

正确：**跨度用 guide 头尾，位置用内部 trace 节点的格位**（只有 3 和 21）。

### 4.2 "已被覆盖"只看长条头部的格位

一条长条可能从格 21 一路滑到格 3。只看头部，就会认为格 3 那一刻没有手指，
于是多发一根 —— 和滑条抢触发。

正确：**按轨迹插值**取那一刻的格位，容差用**这条 trace 自己的 `size/2`**。

## 5. 验证脚本的思路（比脚本本身重要）

不能只验证"动作都发出去了" —— 那只能证明程序没崩。要验证**几何关系**：

### 5.1 每个 trace 节点：那一刻有没有手指在它自己的宽度里

```python
for 每个 trace 节点 t:
    for 每条长条 h:
        if h.time <= t <= h.end:
            lane = 轨迹插值(h, t)          # 不是 h.center
            if abs(lane - center(t)) <= size(t)/2:
                命中
```

结果：**225 / 225**。长条内部的 trace 子节点：**100 / 100**。

### 5.2 排程状态机

```python
for 每个动作:
    down: slot 不能已存在
    move: slot 必须存在
    up  : slot 必须存在
```

结果：**0 违规**；峰值 6 指。

### 5.3 用"结算 miss 数"做最终裁判

单元测试只能证明"我以为的对"，真机结算页才是唯一裁判。所以每局都打对账日志，
并且**先看日志再猜**：

| 日志 | 含义 |
| --- | --- |
| `p95` 很大 | 时间问题（线程/锚点） |
| `p95` 很小但 miss 多 | 手势判定问题（轨迹/宽度/身份） |
| `trace 8 / 41` | 发出去 8 条，谱面共 41 条 |
| `含 auto 滑条 1` | 这一局用了多少条 positionAuto 滑条 |

## 6. 反编译的边界

拿一个"能全连的旧版"来对照是对的，但能得到的只有**实现**：

* 谱面节点逐条相同 → ✅ 说明用的是同一套谱面
* 几何/排程常量完全相同 → ✅ 说明这两块没改
* 它不区分 guide → ❌ **不能推出"所以 guide 都是音符"**

因为它的 guide 走的可能是另一条分支的语义。1.4.9c 就是照抄这条推理崩掉的。

**可用的证据是它的输出，不是它的常量。**

## 7. 一条元教训

这个项目里每一次大翻车，都是因为**用一个间接指标代替了真正的观测量**：

| 间接指标 | 真正该看的 |
| --- | --- |
| "动作都发出去了" | 那一刻手指在不在音符宽度里 |
| "常量一样" | 结算页的 miss 数 |
| "这个版本改过、没用" | 那个版本到底有没有正确实现 |
| "guide 是容器，容器就是长条" | 子节点是 `trace` 还是 `auto` 还是没有 |
