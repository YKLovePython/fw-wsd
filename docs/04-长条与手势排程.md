# 04 · 长条与手势排程

## 1. 几何：判定线位置可以直接算

游戏自己的场景数据（相机/平面/视锥）：

```
判定平面挂在相机前 10.6078
视锥半高 5.4048  ≈  平面自身半高 5.4
```

两者相等意味着 **平面高度 1:1 铺满屏幕高度**，屏幕更宽只是两侧留白。于是：

| 量 | 值 |
| --- | --- |
| 1 平面单位 | `屏高 / 10.8` 像素 |
| 判定线 y | `0.79259 × 屏高`（= `(5.4 − (−3.16)) / 10.8`） |
| 一格宽 | `0.64237` 平面单位 |
| 格位中心范围 | `0 .. 24` |

实测（2510×1156 横屏）：

```
2510x1156  判定线 y=916 (79.24% 屏高)  一格 68.8px  演奏区 825px
```

**所以新手机不需要校准** —— 这个"零标定"不是省了步骤，是几何本来就能从游戏数据里
推出来。31 张全分辨率截图验证：格线间距残差中位数 **−1.1%**。

## 2. 事件 → 动作表

谱面事件最后摊成 `(时刻, down|move|up, slot, x, y)` 的动作表，全部是相对谱面 0 点的
时间。常量：

```python
TAP_MS         = 0.040   # 点击按住 40ms
HOLD_TAIL_PAD  = 0.060   # 长条末尾多按住 60ms 再抬
FLICK_LEAD_S   = 0.020   # 上滑提前 20ms 起手
FLICK_SPAN_S   = 0.050   # 上滑用 50ms 走完
FLICK_DIST     = 120     # 上滑位移 120px
SLOTS          = 9       # 同时最多 9 根手指（上限 10，留一根余量）
RELEASE_GAP_S  = 0.030   # 同一 slot 复用前至少间隔 30ms
MOVE_TARGET_PX = 50      # 长条每移动 50px 补一个 move
MOVE_MIN_S     = 0.025   # move 最快 40Hz
```

## 3. 长条按距离重采样

谱面节点之间大约 **157ms** 一个。如果"每个节点挪一次手指"：

* 中位跳变 **197px**；
* 而音符本身的命中宽度和这个同量级 —— 手指有一半时间在音符外面。

结果就是**间歇性掉**（不是整条掉，是闪一下 miss），非常难查。

改成**按距离补点**：每移动 ~50px 插一个 `move`，且不高于 40Hz。
中位步长从 197px 降到 **72px**，注入速率中位 26/s、峰值 94/s（原来 232/s）。

轨迹来源两条路（见 [02](02-谱面结构与音符分类.md)）：

| 情况 | 位置来源 |
| --- | --- |
| 含 `trace` 节点的 guide | trace 节点自己的格位（不用 guide 的 `pos`，否则出屏） |
| 含 `positionAuto` 的 guide | `_path_of(inner)` 头尾插值（auto 节点没有坐标） |
| 普通 `long` | 容器子节点的 `pos` |

## 4. 长条头尾的两种特殊情况

### 4.1 头是 flick

"先上滑再按住"不是一个动作，是**一根手指的三个阶段**：

```
down(格位) → move(向 +y 120px，20~50ms) → move(回判定线) → 一直按住 → up
```

如果把它拆成"另一根手指上滑 + 这根按住"，游戏会认为按住的那根没滑、上滑的那根没按，
两个都不判。这也是 1.5.0 丢掉 flick 头的代价（`100040` 结尾全 miss）。

### 4.2 尾是 flick

反过来：按住到尾巴，**最后一下滑出去再抬**。顺序必须是
`按住 … → move 出去 → up`，**不能先 up 再滑**。

## 5. 墙（连续同一位置的快速点击）

连续 ≥3 拍、间隔 ≤60ms、中心格位差 <0.7 的同一位置，用**一次下压 + 多次上滑回落**
来表达，而不是 N 次独立 `down/up`：

```python
WALL_MIN_NOTES  = 3      # 连续几拍才算墙
WALL_MAX_GAP_S  = 0.060  # 相邻两拍间隔上限
WALL_SAME_POS   = 0.7    # 同一位置 = 中心格位差 < 0.7
WALL_RETURN_S   = 0.012  # 划到顶之后多久回落（为下一拍留向上位移）
WALL_TAIL_S     = 0.040  # 最后一个音符之后多久抬手
```

原因：60ms 间隔的独立 `up/down` 在 HID 层会产生大量 `TRACKING_ID` 抖动，
游戏端有时会把两次点击并成一次。一次下压 + 小幅往返是稳的。

## 6. 排程一致性

`build_actions` 只保证一件事：**每个 slot 的 down/move/up 严格配对**。

| 违规类型 | 后果 |
| --- | --- |
| 同 slot 重复 down | 后一个被丢掉，那根手指"消失" |
| move/up 没有对应 down | 整条拒绝，屏幕上没有手指 |
| up 后立刻复用同 slot（<30ms） | 内核来不及清 `TRACKING_ID`，下一次按下不生效 |

全库 384 张谱的复查结果：**0 违规**，同时按着的手指峰值 **6**（上限 9）。

## 7. 一个反例：为什么不能"所有容器都当长条"

有个能全连的旧版程序（b1）反编译后，谱面节点逐条相同、几何/排程常量完全相同，
唯一差别是它**不区分 guide**。看起来"照抄它就行"，但 1.4.9c 照抄后崩溃：
因为 b1 里 guide 容器走的是**另一条（`b1` 分支）的语义**，不是简单的"当 long"。
所以"节点一样、常量一样 ⇒ 行为一样"这个推理在这里不成立。

**教训：反编译得到的是实现，不是意图。** 要拿它的**输出**（结算 miss 数）当证据，
不能拿它的常量当证据。
