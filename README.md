# fw-wsd · klkldkdk

《BanG Dream! Our Notes》自动演奏 —— **手机不用 root、不用电脑、不用 Shizuku。**

> 装一个 APK 在手机上，游戏自己打完一整首。只在开发者选项里做一次「无线调试配对」
> （6 位配对码），之后每次打开 App 点一下就行。

[下载最新 APK](https://github.com/YKLovePython/fw-wsd/releases/latest) · [技术笔记](docs/00-技术总览.md) · [使用说明](docs/07-使用说明-Android.md)

---

## 这是什么

两代实现，共用同一套谱面解析与排程内核：

| 代 | 跑在哪 | 一句话 |
| --- | --- | --- |
| **手机版**（当前发布，`klkldkdk` 1.5.1） | 手机自己 | App 内起 `adb` 连自己，视频自己解、手指自己发 |
| PC 版 | Windows + USB / 无线 ADB | 电脑解码视频流做首音符对时，手机只负责被注入 |

触摸注入走 **scrcpy-server 的 UHID 虚拟触摸屏**（`shell` 身份，免 root）：
内核把它当真实外接数位屏，游戏分不出和真手指的区别。
没有 `/dev/uhid` 的机型自动退回 `INJECT_TOUCH_EVENT`。

**已覆盖的手势**：tap、flick（上/左/右）、长条、**会移动的长条**、
长条头/尾接 flick、**Trace 音符**（含 `positionAuto` 自动布点的滑条）。

## 它为什么准

**1. 判定线不用校准，是算出来的。**
游戏自己的场景数据：判定平面挂在相机前 `10.6078`，视锥半高 `5.4048`
＝ 平面半高 `5.4`，所以平面 **1:1 铺满屏幕高度**。于是判定线恒在
**`79.259%` 屏高**、一格宽 `0.64237` 平面单位。
2510×1156 实测：`y=916 (79.24%)`、一格 `68.8px`。
31 张全分辨率截图的格线间距残差中位 **−1.1%** —— 换手机不需要重新校准。

**2. 开局 0 点是量出来的，不是等出来的。**
"点完 LIVE START 到音乐开始"在同一台机器同一天实测过
**2.12s / 9.53s / 10.05s / 11.52s** —— 差 9 秒，任何固定等待都是掷骰子。
这里用两条互相独立的尺子量：**加载页亮→黑**（信号极大，抗掉帧）
与**判定线淡入**（1~2px，怕掉帧），亚帧插值取 0.5 穿越点，再互相交叉校验。

**3. 长条按距离重采样。**
谱面节点约 157ms 一个；"每个节点挪一次手指"的中位跳变是 **197px**，
和音符自身命中宽度同量级 → 手指一半时间在音符外，表现为**间歇性闪 miss**。
改成每移动 ~50px 补一个 `move`（≤40Hz），中位步长降到 **72px**。

**4. 手指身份按 HID 规范做。**
每根手指固定 slot、`Contact Identifier` 恒等于 slot 号，抬手只清
`Tip Switch / In Range`。否则内核不产生 `ABS_MT_TRACKING_ID = -1`，
系统眼里手指永远按着 —— 症状是**整首只有第一个音符能判定**，而日志上一切正常。

## 它踩过的坑（也是这套笔记最贵的部分）

`guide` 容器看起来就是长条，但 **614 条里只有 41 条含 `trace`、253 条含
`positionAuto`，剩下 328 条是视觉参考线。**

把 614 条全发（1.4.9c）：开局就按 3 根手指、按住 10 秒，**整局全 miss**。
这不是"多按了几个"，是那根假手指把真音符的触摸槽位抢走了 ——
**在触摸判定里，多发的手指是有害的，不是无害的冗余。**

完整复盘（含五个被证伪的版本、两个"看起来对"的错误判据）：
[`docs/05-踩坑与验证.md`](docs/05-踩坑与验证.md)
